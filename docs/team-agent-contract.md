# FirstListen 3인 팀 · AI 에이전트 호출 규약

이 문서는 세 팀원이 각자의 AI 코딩 에이전트에 전달하는 공통 작업 규약이다. 제품 목표, 현재 백엔드 API 계약, 담당 경계, 구현 순서, 검수 기준을 고정해 에이전트가 서로 다른 가정을 코드로 만들지 않도록 한다.

## 1. 프로젝트 기준

FirstListen은 Android에서 YouTube Music 청취 세션을 관찰해 개인별 청취 이력을 저장하고, 사용자가 곡별 최초 기록일과 누적 청취 시간을 확인하도록 돕는 앱이다.

- **현재 구현됨:** FastAPI 백엔드의 인증, 회원별 청취 이벤트 동기화, 곡 검색·상세·통계, 제한된 자연어 질문 조회.
- **팀의 주요 구현 대상:** Android 권한·재생 세션 수집, 로컬 영속 저장과 오프라인 동기화, 최소 권한의 사용자 화면, 실제 기기 검증.
- **후속 범위:** 대화 문맥, 월간 리포트, 별도 웹 앱. (기간·순위 같은 자유 통계 질문은 Text-to-SQL로 이미 구현되어 있다.) 팀의 합의 없이 MVP에 끼워 넣지 않는다.
- **기록의 의미:** YouTube Music이 제공하고 앱이 관찰한 데이터만 기록한다. 설치 전·수집 중단 중의 재생은 복원할 수 없으며, 총 시간은 실제 재생 시간을 완벽히 측정한다는 보장이 없는 관찰값이다.
- **기술 기준:** Android는 Kotlin, Jetpack Compose, Room, WorkManager를 기본 방향으로 한다. 백엔드는 Python 3.12+, FastAPI, Pydantic, SQLAlchemy, Alembic, PostgreSQL이다.

백엔드는 이 저장소의 `app/`에 이미 있다. API를 임의로 재설계하지 말고 [OpenAPI 계약](./openapi.json)과 아래 계약을 따른다. 구현과 문서가 다르면 먼저 기존 코드·OpenAPI·README를 확인하고, API 변경이 꼭 필요하면 팀 합의를 얻은 뒤 서버·클라이언트·테스트·OpenAPI를 함께 수정한다.

## 2. MVP의 완료 조건

1. 사용자가 회원가입·로그인하고 앱을 다시 열어도 인증 상태를 안전하게 복구할 수 있다.
2. Android 권한을 사용자에게 설명하고 허용 여부를 확인한 뒤, 지원되는 재생 세션을 관찰한다.
3. 세션 이벤트를 기기에 영구 저장한다. 네트워크가 없어도 이벤트가 사라지지 않고, 재시작 후에도 동기화를 이어간다.
4. 30초 이상 관찰된 이벤트만 서버 기록·집계에 반영한다. 동일 세션의 재전송·시간 갱신은 중복 합산되지 않는다.
5. 사용자는 본인 곡 목록에서 곡을 찾아 최초 기록 시각과 관찰된 총 청취 시간을 확인할 수 있다.
6. 사용자는 선택한 곡 또는 질문에 명시한 곡에 대해 지원 범위 안의 자연어 질문을 할 수 있다. 곡이 모호하면 사용자가 선택할 때까지 결과를 추측하지 않는다.
7. 권한 거부, 오프라인, 토큰 만료, 서버 오류, 빈 기록 상태가 오류나 데이터 손실 없이 설명된다.
8. 주요 동작을 자동 테스트하고, 권한·화면 잠금·일시정지·건너뛰기·오프라인·재부팅을 실제 Android 기기에서 확인한다.

## 3. API 호출 계약

### 공통

- 기본 로컬 API 주소는 `http://localhost:8000`이다. Android Emulator에서 개발 PC의 API에 접근할 때는 환경별 주소 설정을 사용한다(일반 Emulator에서는 `10.0.2.2`가 호스트를 가리킨다). 실기기는 같은 네트워크의 개발 PC 주소를 사용한다. 주소를 코드에 고정하지 않는다.
- 서버는 기본적으로 개발 PC 안(`127.0.0.1`)에서만 열린다. Emulator(`10.0.2.2`)는 그대로 접속되지만, 실기기 테스트 때는 서버를 `API_BIND=0.0.0.0 docker compose up -d`(직접 실행 시 `uvicorn ... --host 0.0.0.0`)로 띄운다.
- Android 9 이상은 `http://` 평문 통신을 기본 차단한다. **디버그 빌드에서만** `network_security_config`로 개발 서버 주소(`10.0.2.2`, 개발 PC IP)의 평문 HTTP를 허용하고, 릴리스 빌드는 HTTPS만 사용한다. `usesCleartextTraffic=true`를 앱 전체에 켜지 않는다.
- API 문서와 실행 가능한 계약은 `GET /docs` 및 `docs/openapi.json`에서 확인한다. 앱의 API 기본 경로는 `/api/v1`이다.
- `/health`, `/ready`를 제외한 사용자 API에는 `Authorization: Bearer <access_token>`을 보낸다. 사용자 ID를 경로나 요청 본문으로 보내지 않는다.
- 날짜·시각은 타임존이 포함된 ISO 8601 형식으로 주고받는다. API 저장 시각은 UTC이며 날짜를 사용자에게 보여줄 때 기본 시간대는 `Asia/Seoul`이다.
- JSON 외 응답의 세부 오류 문구에 의존하지 않는다. HTTP 상태 코드와 응답 스키마를 기준으로 분기하고, 사용자가 조치할 수 있는 메시지를 표시한다.

### 인증 및 회원

| 목적 | 호출 | 성공 응답 | 주요 오류 |
|---|---|---|---|
| 가입 | `POST /api/v1/members` | `201`, `{ "id": "<uuid>", "email": "you@example.com" }` | `409` 이미 가입된 이메일, `422` 형식 오류, `429` 요청 제한 |
| 로그인 | `POST /api/v1/auth/login` | `200`, `{ "access_token": "...", "token_type": "bearer", "expires_at": "<date-time>" }` | `401` 이메일·비밀번호 불일치, `422`, `429` |
| 현재 회원 확인 | `GET /api/v1/members/me` | `200`, 회원 `id`, `email` | `401` 토큰 없음·만료·폐기 |
| 로그아웃 | `POST /api/v1/auth/logout` | `204`, 응답 본문 없음 | `401` |

가입·로그인 본문은 `{"email":"you@example.com","password":"10자 이상의 비밀번호"}`다. 이메일은 서버에서 대소문자를 구분하지 않는다. 비밀번호는 앞뒤 공백도 비밀번호의 일부이므로 앱에서 trim하지 않는다. 길이는 10~128자다. 토큰은 만료 시각을 확인해 안전한 기기 저장소에 보관하고, 로그아웃 시 서버 호출 성공 후 로컬 토큰도 지운다.

- **토큰 갱신(refresh) API는 없다.** 토큰 유효기간은 기본 30일(`expires_at`)이다. 만료 시각이 지났거나 보호 API가 `401`을 반환하면 로컬 토큰을 지우고 재로그인 화면으로 보낸다. 존재하지 않는 갱신 엔드포인트를 만들거나 호출하지 않는다.
- **요청 제한:** 가입·로그인은 IP당 분당 10회, 질문(`/chat`)은 사용자당 분당 20회다. 초과하면 `429`와 `Retry-After`(초)를 반환한다. Emulator에서 로그인을 반복 테스트하면 쉽게 걸리므로 자동 재시도 루프를 만들지 않는다. 동기화와 곡 조회에는 요청 제한이 없다.

### 청취 이벤트 동기화

`POST /api/v1/listens/sync`는 한 번에 1~100개 이벤트를 받는다.

```json
{
  "events": [
    {
      "event_id": "3c473c97-0a37-4d64-99be-18574b1cec08",
      "track": {
        "title": "입춘",
        "artist": "한로로",
        "album": null,
        "external_id": "youtube-music-track-id"
      },
      "observed_at": "2026-11-06T15:00:00+09:00",
      "listened_ms": 31000
    }
  ]
}
```

각 결과는 `{ "event_id": "<uuid>", "status": "accepted" | "ignored_below_threshold", "track_id": "<uuid 또는 null>", "listened_ms": "<정수 또는 null>" }` 형태이며, 응답 최상위 키는 `results`다.

**클라이언트 필수 규칙**

1. 재생 세션이 시작될 때 UUID `event_id`를 한 번 만든다. 해당 세션의 모든 재시도와 누적 시간 갱신에 같은 ID를 사용하고, 반복 재생은 새 ID를 만든다.
2. `event_id`, 최초 `observed_at`, 곡 식별 정보, 누적 `listened_ms`를 Room에 영속 저장한다. 재시도할 때 이벤트 ID를 새로 만들지 않는다.
3. `observed_at`은 세션의 최초 관찰 시각이며 타임존을 포함한다. 세션 시간 갱신 때문에 최초 시각을 현재 시각으로 덮어쓰지 않는다.
4. 서버는 같은 이벤트의 가장 이른 관찰 시각과 가장 큰 누적 시간을 유지한다. `listened_ms`는 델타가 아니라 해당 이벤트의 누적 밀리초다. `31,000 → 120,000 → 31,000`을 보내도 최종 집계는 이벤트 한 개, 120,000ms다.
5. 30,000ms 미만은 `ignored_below_threshold`로 저장·집계되지 않는다. 아직 진행 중인 세션은 같은 ID로 누적값을 계속 동기화할 수 있어야 한다. 서버가 `accepted`를 반환한 이벤트도 진행 중 세션의 새 누적값을 보낼 때 동일 ID를 유지한다.
6. `accepted` 결과의 `track_id`를 곡 상세·통계·질문 조회에 사용한다. 클라이언트가 임의로 곡 UUID를 생성하지 않는다.
7. 네트워크 실패·`5xx`는 지수형 재시도와 상한을 두고 재시도하되, 동일 이벤트 ID와 동일하거나 더 큰 누적값을 전송한다. `Retry-After`가 있는 `429`는 그 시간을 따른다. 인증 `401`은 재로그인 흐름으로 처리한다(토큰 갱신 API 없음). 재로그인 후 같은 이벤트 ID로 다시 보낸다. 입력 오류 `422`와 ID-곡 충돌 `409`는 자동 반복하지 않고 사용자/진단 가능한 오류로 처리한다.
8. 한 배치에서 이벤트 ID를 다른 곡에 재사용하면 `409`이며 배치 전체가 롤백된다. 배치가 원자적이므로 부분 성공을 가정하지 않는다. 응답 `results`를 확인한 뒤 해당 상태를 로컬 큐에 반영한다.
9. 최소 임계값 판정은 서버의 응답을 기준으로 한다. 클라이언트에서 짧은 세션을 아예 버리면 이후 누적 갱신 기회를 잃을 수 있으므로, 서버 응답 전에는 로컬 이벤트를 삭제하지 않는다.

서버 검증 범위는 `listened_ms` 정수 0~86,400,000, 시간대가 있는 `observed_at`, 현재보다 5분 이상 미래가 아닌 시각이다. `track.title`·`artist`는 1~300자, `album`은 nullable 최대 300자, `external_id`는 nullable 최대 200자다.

### 곡 목록·상세·통계

| 목적 | 호출 | 주요 응답 |
|---|---|---|
| 내 곡 검색·페이지 조회 | `GET /api/v1/tracks?q=<검색어>&limit=20&offset=0` | `{ "items": [Track], "total": 0, "limit": 20, "offset": 0 }` |
| 곡 상세 | `GET /api/v1/tracks/{track_id}` | `Track` |
| 곡별 통계 | `GET /api/v1/tracks/{track_id}/stats` | `{ "track": Track, "first_recorded_at": "<date-time 또는 null>", "total_listened_ms": 0, "event_count": 0 }` |

`Track`은 `{ "id": "<uuid>", "title": "...", "artist": "...", "album": "<문자열 또는 null>", "external_id": "<문자열 또는 null>" }`다. `q`는 최대 300자, `limit`은 1~100(기본 20), `offset`은 0~100,000(기본 0)이다. 페이지의 빈 목록과 통계의 `first_recorded_at: null`은 정상적인 빈 상태로 보여준다. 모든 검색과 조회는 로그인한 본인의 곡만 대상으로 한다.

### 자연어 질문

`POST /api/v1/chat` 요청은 `{"question":"입춘 언제부터 들었어?"}` 또는 `{"question":"이 노래 총 재생 시간이 얼마야?","track_id":"<선택한 곡 UUID>"}`다. 질문은 1~500자이며 `track_id`는 선택 사항이다.

응답에는 `status`, `answer`, `metric`, `track`, `candidates`, `first_recorded_at`, `total_listened_ms`, `rows`가 있다. `status`는 `answered`, `needs_track`, `ambiguous`, `not_found`, `unsupported` 중 하나다. `metric`은 nullable한 `first`, `total`, `both`, `stats` 중 하나다. `debug` 필드는 서버 개발·평가용(`CHAT_DEBUG=true`)으로만 채워지므로 앱에서 사용하지 않는다.

**결과 표시 방법**

- 모든 상태에서 `answer`는 서버가 만든 한국어 문장이다. 기본으로 이 문장을 그대로 표시한다.
- `metric`이 `first`/`total`/`both`이면 `first_recorded_at`(UTC, 표시할 때 `Asia/Seoul`로 변환)과 `total_listened_ms`(밀리초)를 구조화된 값으로 함께 쓸 수 있다.
- `metric`이 `stats`이면 결과는 `rows`(최대 50행)에 있다. **열 이름은 질문마다 LLM이 정하므로 고정 스키마로 파싱하지 않는다.** `rows`를 표로 보여주려면 첫 행의 키를 열 제목으로 쓰고, 이름이 `_ms`로 끝나는 열은 밀리초이므로 시간 형식으로 바꿔 표시한다. 표를 만들지 않아도 `answer`만으로 결과가 전달된다.

- `answered`: 서버가 계산한 결과를 표시한다.
- `needs_track`: “이 노래”를 가리키는 `track_id`가 아직 없다. 곡을 선택하게 한다.
- `ambiguous`: 후보가 여러 개다. `candidates`에서 한 곡을 고르게 하고 선택한 `track.id`로 다시 요청한다. 임의로 첫 후보를 고르지 않는다.
- `not_found`: 해당 사용자 기록이 없다. 결과를 추측하지 않는다.
- `unsupported`: 현재 지원하지 않는 질문이다. 지원 범위를 안내한다.

지원 질문은 본인 청취 기록의 최초 기록일·총 청취 시간 및 현재 지원되는 통계다. 타 사용자 조회, 기록 변경·삭제, 자유 대화는 지원된다고 가정하지 않는다. LLM 키가 없거나 호출이 실패하면 일부 질문은 규칙 기반 분류로 처리되며 자유 통계는 지원되지 않을 수 있다. 따라서 클라이언트는 질문을 LLM이 항상 답할 것이라고 가정하지 않는다.

## 4. 3인 담당 및 파일 경계

먼저 통합 담당자가 저장소 상태를 확인한다. 아직 Android 모듈이 없다면 Gradle 프로젝트 이름, `android/` 하위 구조, 최소 SDK, 권한·배포 기준을 짧게 합의하고 Android 모듈 생성은 한 에이전트만 담당한다. 세 에이전트가 동시에 빌드 설정이나 공통 네트워크 계층을 만들지 않는다.

| 담당 | 주 목표 | 맡는 영역 | 맡지 않는 영역 |
|---|---|---|---|
| 팀원 A — 수집·로컬 저장 | 재생 세션 관찰과 유실 없는 이벤트 큐 | 미디어 세션/알림 권한, 세션 상태 추적, `Room` 엔티티·DAO·마이그레이션, 세션별 UUID와 누적 시간 | 화면 전체, 서버 API 의미 변경 |
| 팀원 B — 앱·API 흐름 | 사용자가 기능을 시작하고 결과를 보는 화면 및 API 연동 | 회원가입·로그인, 권한 안내·설정, 곡 목록/상세/통계/질문 화면, API client·인증 헤더·화면 상태 | 수집기의 내부 구현, 이벤트 저장 의미 재정의 |
| 팀원 C — 계약·통합 검증 | 클라이언트와 기존 백엔드의 호환성 및 MVP 통합 | 기존 API/OpenAPI 검증, API·동기화 통합 테스트, 테스트용 시나리오/fixtures, 이슈 재현·통합 점검, 필요 시 합의된 백엔드 수정 | Android 기능을 임의로 중복 구현, 동의 없는 API 변경 |

### 경계·통합 합의

- 팀원 A와 B는 이벤트 모델과 API DTO를 공통 문서/모듈에 선언된 타입으로 공유한다. `event_id`, `observed_at`, 누적 `listened_ms`, 서버 `track_id`의 의미를 각자 다르게 정의하지 않는다.
- 인증 토큰 저장·첨부는 B가 소유하는 공통 API 계층에서 한다. A는 네트워크 호출이 필요하면 B의 동기화 인터페이스를 사용하고 HTTP client를 따로 만들지 않는다.
- A는 Room에 저장한 이벤트의 읽기/전달 인터페이스를 공개한다. B는 그 저장소 구현을 복제하지 않는다. C는 이 경계에 대한 계약 테스트와 통합 시나리오를 소유한다.
- 공유 파일이나 Gradle 설정을 바꾸기 전에 담당자끼리 알린다. 서로의 담당 파일을 직접 수정하지 말고 인터페이스 변경 제안을 먼저 보낸다.
- API 계약 변경은 C가 근거와 영향을 기록하고 팀이 동의한 뒤 진행한다. 서버 구현, Pydantic 스키마, OpenAPI snapshot, 앱 DTO, 테스트를 한 변경 묶음으로 갱신한다.
- 기능을 연결하는 시점에는 작은 수직 흐름(로그인 → 권한/수집 → 로컬 저장 → 동기화 → 곡 목록 → 통계)을 먼저 끝낸다. 화면이나 모듈을 대량으로 병렬 생성해 마지막에 합치지 않는다.

## 5. 각 팀원이 AI 에이전트에 보내는 프롬프트

각 프롬프트 앞에 **공통 지시문**을 붙이고, 아래 담당 프롬프트 하나만 추가한다. 에이전트가 코드를 수정하기 전에 기존 파일과 git 변경 사항을 확인하고, 담당 밖의 파일을 수정해야 하면 먼저 이유·영향·대안을 보고하게 한다.

### 공통 지시문 (세 에이전트 모두 복사)

> 우리는 3인 팀으로 FirstListen MVP를 구현한다. 제품 및 API의 기준은 `README.md`, `docs/team-agent-contract.md`, `docs/openapi.json`이다. 이 문서에서 현재 백엔드가 구현됨과 Android가 후속 구현 범위임을 구별하라. API는 문서와 실제 스키마에 있는 계약을 그대로 사용하고, 사용자 ID를 클라이언트에서 보내거나 다른 사람의 데이터를 조회하지 마라.
>
> 시작할 때 작업 트리와 관련 코드를 읽고, 내가 맡은 범위·수정할 파일·접점·테스트 계획을 짧게 제시하라. 합의된 담당 경계를 지키고, 필요 이상의 리팩터링·의존성 추가·API 확장은 하지 마라. 비밀키와 실제 사용자 데이터를 저장소나 로그에 남기지 마라. 오류를 조용히 삼키지 말고 로딩/성공/빈 상태/권한 거부/오프라인/인증 만료/서버 오류를 구별하라.
>
> 구현 후에는 변경 파일과 동작을 요약하고, 실행한 테스트·결과 및 남은 한계를 보고하라. 실패한 검증을 성공으로 표현하지 마라. 다른 담당 영역의 변경이 필요하면 수정 전에 이유, 영향받는 계약, 담당자 확인이 필요한 결정을 밝혀라.

### 팀원 A 추가 프롬프트 — 수집·로컬 저장

> 너의 담당은 Android 재생 세션 관찰, 세션 이벤트 생성, Room 영속 큐와 그 테스트다. 기존 프로젝트 구조와 Android API 지원 여부를 먼저 확인하라. 필요한 권한은 최소화하고, 권한 요청 전에 사용 목적과 설정 경로를 설명하라. 화면 잠금/프로세스 재시작/네트워크 단절에서도 데이터가 유실되지 않도록 설계하라.
>
> 세션 시작 시 UUID를 한 번 만들고 같은 세션의 재시도·누적 갱신에 유지하라. 관찰 최초 시각을 유지하고 `listened_ms`는 누적값으로 저장하라. 30초 미만 이벤트도 진행 중이라면 나중에 같은 ID로 임계값을 넘겨 보낼 수 있도록 보존하라. 서버 동기화 자체를 새로 구현하지 말고 팀원 B와 합의한 동기화 인터페이스에 이벤트 큐를 제공하라.
>
> 담당 범위의 단위 테스트를 추가하라: 세션별 ID 안정성, 누적 시간 갱신, 영속 저장/복구, 중복 재전송, 임계값 전후 동작. Android에서 관찰할 수 없는 상태를 확정 사실로 기록하지 말고 관찰 한계를 명시하라.

### 팀원 B 추가 프롬프트 — 앱 화면·API 연동

> 너의 담당은 Android 사용자 흐름, 최소 화면, 인증과 API 호출 계층이다. 서버 계약에 맞춰 가입/로그인, 토큰 안전 저장, 본인 곡 목록·상세/통계, 자연어 질문, 권한 안내·빈 상태·오류 상태를 구현하라. API 주소는 환경별로 설정 가능해야 하며 비밀값이나 토큰을 로그에 출력하지 마라.
>
> `Bearer` 인증은 보호 API에만 붙이고 로그인·가입 요청에는 기존 토큰을 요구하지 마라. 질문 응답의 다섯 상태를 각각 처리하라. `ambiguous`면 후보 선택 후 선택한 `track_id`로 재요청하고, `needs_track`면 현재 선택 곡을 전달하도록 유도하라. `401`, `404`, `422`, `429` 및 네트워크/`5xx` 오류를 구분하라. 서버가 반환한 `track_id`만 곡 참조에 사용하라.
>
> 이벤트 저장/수집 로직은 직접 복제하지 말고 팀원 A의 저장소/인터페이스를 사용하라. UI 테스트 또는 API 계층 테스트를 추가해 로딩·빈 목록·모호한 곡·오프라인·인증 만료 동작을 확인하라.

### 팀원 C 추가 프롬프트 — 계약·통합 검증

> 너의 담당은 현재 FastAPI 구현과 OpenAPI를 기준으로 계약을 확인하고, Android 연동을 검증할 재현 가능한 테스트와 통합 시나리오를 제공하는 것이다. 서버가 이미 구현한 기능을 다시 만들지 말고, README·라우터·Pydantic 스키마·테스트·`docs/openapi.json`의 차이를 확인하라.
>
> 우선 회원 인증, 이벤트 동기화, 곡 검색·통계, 질문 응답 상태, 사용자 간 데이터 격리 테스트를 실행하라. Android 클라이언트가 소비할 성공·오류 응답을 명확히 정리하고, 특히 같은 이벤트의 재전송/누적 갱신, 30초 미만 이벤트의 추후 승격, 409 배치 롤백, `Retry-After`, 모호한 질문 후보 선택을 검증하라. 필요한 경우 테스트 계정은 개발용 DB에서만 사용한다.
>
> 백엔드 코드 변경은 테스트나 명시된 API 계약에서 확인된 결함에 한정하라. 계약 변경이 불가피하면 먼저 영향과 호환성 방안을 보고하고, 동의 후 서버·스키마·OpenAPI·클라이언트 DTO·회귀 테스트를 함께 갱신하라. 결과는 재현 명령과 통과/실패를 구분해 보고하라.

## 6. 작업 및 검수 프로토콜

1. **통합 담당자 확인:** 기준 브랜치와 작업 트리를 확인하고, Android 모듈·빌드 환경·API 주소를 팀이 공유한다. 기존의 미커밋 변경은 소유자 확인 없이 덮어쓰지 않는다.
2. **계약 우선:** 팀은 이벤트 필드와 상태 전이, 공용 인터페이스, API base URL 설정 방법을 확정한다. 불확실한 권한/기기 호환성은 기기 실험으로 확인한다.
3. **작은 병렬 작업:** 각 에이전트에 담당 한 가지와 수정 허용 영역, 테스트 조건을 지정한다. 병렬 작업은 파일이 겹치지 않을 때만 한다. 인터페이스가 바뀌면 즉시 관련 담당자에게 알린다.
4. **개별 검증:** 각 담당자는 변경 영역의 가장 작은 관련 테스트와 빌드/정적 검사를 실행하고 결과를 공유한다.
5. **통합 검증:** 로그인부터 로컬 이벤트 동기화와 통계 조회까지 한 번에 실행한다. API 스키마가 바뀌었다면 `python scripts/export_openapi.py` 후 변경 diff를 확인하고, 회귀 테스트와 Postman 컬렉션을 다시 검증한다.
6. **기기 검증:** 화면 잠금, 재생/일시정지/건너뛰기, 반복 청취, 오프라인 큐 적재, 재연결, 앱/기기 재시작, 권한 거부를 기록한다.
7. **완료 보고:** 담당별 변경 파일, 수동·자동 검증 결과, 실제 기기/에뮬레이터 범위, 알려진 제한 사항을 한눈에 공유한다. 검증 안 된 동작을 완료로 표시하지 않는다.

### 공통 테스트 시나리오

- 동일 이벤트를 `31,000 → 120,000 → 31,000ms`로 동기화했을 때 이벤트 수는 1, 최종 누적 시간은 120,000ms다.
- 30초 미만 이벤트가 `ignored_below_threshold`여도 같은 ID의 후속 누적값이 기준을 넘으면 기록된다.
- 오프라인 동안 Room에 쌓인 이벤트가 재연결·앱 재시작 후 동일 이벤트 ID로 동기화된다.
- 사용자 A의 곡 ID를 사용자 B가 조회하면 곡 존재 여부가 노출되지 않는 `404`다.
- 곡명으로 질문해 후보가 여러 개면 `ambiguous`를 표시하고, 곡 선택 전에는 통계가 표시되지 않는다.
- `401`은 재로그인 흐름(토큰 갱신 API 없음), `429`는 `Retry-After`, `5xx`는 재시도 가능성, `422`/`409`는 재시도하지 않는 오류 흐름으로 처리된다.
- 계정·곡·청취 이력이 하나도 없는 상태가 정상적인 빈 화면으로 동작한다.

## 7. 에이전트가 임의로 결정하면 안 되는 것

- 청취 임계값, `observed_at`의 의미, 누적/증분 시간의 의미, UUID 생성·재사용 규칙.
- API 경로·필드명·응답 상태, 인증 저장 방식, 사용자 간 데이터 격리.
- 새로운 권한·민감 정보 수집, 이벤트 삭제 정책, 추적/분석 SDK 도입.
- 대화 기록 저장, 임의 SQL 실행, 타 사용자 데이터 접근, 현재 MVP에 없는 기능 범위.
- Android 모듈의 공용 인터페이스나 다른 담당자의 파일을 알리지 않고 변경하는 것.

이 결정을 바꿔야 할 이유가 있으면 코드부터 수정하지 말고, 근거·대안·보안/호환성 영향·테스트 계획을 팀에 제안한다.
